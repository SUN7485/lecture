Trigger: only if a future preset uses such a family.

- **Deck-CSS specificity beats kit fonts** (accepted limit, by design): decks whose own CSS targets titles with higher specificity than `.slide h1` keep their font when a kit/typography is applied. Trigger: imported decks with aggressive stylesheets. Popover live sample makes it visible; no fix planned.
- **~~Doctor silent on external `@import`~~ → RESOLVED 2026-07-16 by Rule 19b** (`fonts-external`, commit `c698efa`): the doctor now emits a deck-level warn when the deck loads fonts from a web-font host (`@import`/`<link>` to fonts.googleapis.com, typekit, bunny, …), routing the user to 🔤 embed. Verified firing on `Chp1-Lec1-2.html` (Cairo, score 72→68), silent on clean templates. **Deliberate boundary (not a bug):** a distinctive *local-install* font that HAS a generic fallback (e.g. templates' `'Diodrum Arabic', 'Cairo', sans-serif`) is still NOT flagged — it degrades to the fallback rather than tofu, and flagging every such stack would nag the responsible offline-stack design v4 exists to respect. Only the network-dependency case (a fact, zero false positives) is surfaced.
- **~~Theme kits cannot recolor hardcoded hex~~ → RESOLVED 2026-07-26** (kit variable adoption + doctor Rule 21 `hardcoded-colors`): kits now adopt every color variable the deck invented (`--gold`, `--light-cyan`, `--green` → nearest kit token, declared inside `ve-theme`), and the doctor rewrites literal colors in CSS rules, inline styles and SVG `fill=`/`stroke=` attributes to `var(--ve-k-token, #original)`. Measured on the real lectures via `verify-030.js`: on-brand computed colors 73%→100% (Lec34), 70%→100% (Lec35), 99%→100% (2.html), fix-all converges in ≤2 passes with 0 cards left, and switching the identity off restores the authored deck **exactly** (census identical). Same numbers in the web shell.
- **Monospace stays off-brand** (accepted 2026-07-27): `<span>`/`<code>` set to the generic `monospace` family (variable and formula notation — 10–34 elements in the real lectures) renders the system mono font, because MiM ships no monospace face. Forcing Diodrum on them would break the column alignment the notation relies on. Everything else in those decks renders Lyon or Diodrum. Trigger: decks with mathematical notation.
- **A deck's own `font-family` rule can still outrank the kit's role rules** (accepted, unchanged): the kit sets headings via `.slide h1` (0,1,1) and body via `body`/`p`/`li` — a deck rule with higher specificity (e.g. `#id .cover .title`) keeps its own family. Same accepted limit as the older "Deck-CSS specificity beats kit fonts" note; no `!important`, because that would stop the editor's own 🔤 font tools from overriding the kit.
- **The app's own visual generators still emit literal colors** (logged 2026-07-26, not urgent): `src/enrich/charts.js` (17) and `src/enrich/diagrams.js` (14) write `fill="#413258"` into generated SVG because they receive the palette as a bare hex array, so Studio-generated visuals need a doctor pass to become kit-responsive like the rest of the deck. Proper fix: pass the palette as `[{name,value}]` from the pipeline and emit `fill="var(--name, #value)"` — **verified 2026-07-26 that `var()` works in SVG presentation attributes** in this runtime (attribute, fallback and `<text>` forms all resolve). Trigger: Studio charts/diagrams in the Electron app. Harmless meanwhile — Rule 21 catches them.
- **Brand snapping flattens multi-stop gradients** (accepted 2026-07-26): when every stop of a `linear-gradient` snaps to the same kit token the gradient renders as a flat color (Lec35's green cover → solid MiM purple — clean and on-brand, but no longer a gradient). The guide's official gradients (`#825DEC→#3F3355`, `#BFA19F→#efcac7`, `#1AD9C7→#66d6c7`) are the proper future targets; `#825DEC` was deliberately NOT added to the snap palette because it would then scatter into body text. Trigger: any kit applied to a deck with gradient heroes.
- **Semantic colors lose their meaning under a kit** (accepted 2026-07-26): a deck's `--red` warning / `--green` success snap to the nearest MiM color (pink / teal-or-purple) because the ministry palette has no semantic colors. Deliberate trade — brand compliance is the point of the button — and fully reverted by toggling the identity off. Trigger: decks that color-code by meaning.
- **Rewritten stylesheets are re-serialized from CSSOM** (cosmetic, 2026-07-26): a `<style>` the color fix touches is written back from `cssRules[].cssText`, which normalizes `#hex` to `rgb()` and drops CSS comments in that sheet. Semantically identical, but a diff of the saved file looks noisier than the change really is. Untouched sheets are left byte-for-byte alone.

- **~~The fidelity gate is calibrated on synthetic content, so real lectures read RED~~** (2026-08-16, superseded by the line above): `DEFAULT_THRESHOLDS.ssim = 0.8487` was derived (mission 034) from `test/fixtures/calibration-deck.html`, whose worst slide — dense Arabic text in Arial — scores 0.8538. - **~~PowerPoint COM littered the project root with junk directories~~ → FIXED 2026-08-16**: the PowerShell/COM render inherited the caller's cwd, and PowerPoint resolves some cache folders relative to it, creating directories named from uninitialised bytes (34 of them, each holding an empty `Microsoft` folder) during the corpus runs. - **PowerPoint resolves bidi neutrals differently from Chromium** (2026-08-16, diagnosed, fix deliberately deferred): a colon or bracket sitting between an Arabic run and a number/Latin run lands on the other side of it — «الدرس 33: الحل» exports as «الدرس :33الحل», and the following space is swallowed. Reproduce with `node verify-pptx-corpus.js test/fixtures/bidi-deck.html --no-cache`. **Our data is not at fault:** the measured line runs are in LOGICAL order and `concat(runs) === line.text` exactly (verified), and the paragraph carries OOXML `rtl="1"` — so the text handed over is the correct source string and PowerPoint's own bidi algorithm settles the neutral differently. The standard remedy is to wrap number/Latin segments in Unicode isolates (U+2066 LRI … U+2069 PDI), which forces both engines to the same resolution. **Not done, on purpose:** it injects invisible control characters into the user's exported text, which the structural audit compares against `expectedDomText` and which would then live inside every deck the user edits by hand. Cost/benefit is currently poor — the isolated `bidi-deck` fixture still scores **0.9262 SSIM and verifies**, so this is cosmetic-but-visible rather than a gate failure. Revisit if a user complains about the punctuation, or if per-segment measured geometry ever lands (which would allow positioning each segment instead of mutating text).
- **PPTX bake crops carry their backdrop, and clip what overflows** (2026-08-14, mission 033): a baked element (inline SVG, filtered/blended/transformed box) is a crop of the composed page at the node's bounds, so it includes whatever is painted behind it, and any label the element draws *outside* its own bounding box is cut off — visible on the Lec32 linear-programming figure, whose axis labels overflow the `<svg>` box. Overlapping higher-z text above a baked element also double-renders. Trigger: any deck with inline SVG. The self-heal loop (mission 035) is the net; a per-element isolated capture was deliberately rejected in the plan (D1).
- **~~PPTX export: cairosvg not installed~~ → RESOLVED 2026-08-14 (mission 033)**: the cairosvg/inkscape/placeholder rasterizer tiers are gone. Chromium is now the only rasterizer (plan decision D1) — unmappable elements are captured by the same engine that renders the fidelity reference, and a missing capture is a hard error instead of a labeled placeholder that the structural audit could not distinguish from a real picture.
- **Inline `<svg>` was silently dropped from every PPTX before 2026-08-14** (fixed in mission 033, recorded because it explains old exports): `forbiddenTags` held `'SVG'` but DOM `tagName` for a foreign-namespace element is the authored lowercase `'svg'`, so the check never matched. The SVG was walked as ordinary layout nodes that emit nothing — no error, no placeholder, just a missing diagram. Verified in the live DOM and fixed by upper-casing the tag before the lookup.
