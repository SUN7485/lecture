## From the hosted build, 2026-09-02 (see DEPLOY.md)

### Fixed 2026-09-10 during the pre-launch review gate
- **~~One conversion froze the whole server~~ → FIXED (worker pool).** `modelFromPdf` and `writePptx` are synchronous; on the request thread they blocked Node's event loop for their whole duration. Measured: `/healthz` **51ms idle → 2847ms** during ONE ordinary 21-page conversion, which also starves the container healthcheck so the orchestrator restarts a server that is merely busy. All CPU-bound engine work now runs in `server/lib/pool.js` (2 workers, bounded queue, per-job timeout, respawn on death). Re-measured: **9ms max**. Locked by `test/server-hosted.test.js`.
- **~~No page or object budget on the hosted convert~~ → FIXED.** The local studio had capped at 200 pages since long before; the hosted path shipped with only a 25MB byte cap. Page count is now read from the trailer and checked BEFORE extraction (a budget checked afterwards has already paid the cost): a 250-page PDF is refused in **142ms**.
- **~~An export payload could occupy the service for minutes~~ → FIXED.** `objects[]` was unbounded: 20k synthesized objects took 8.9s, 60k took **124 seconds** (superlinear). Now capped at 20,000 entries — the same 60k payload is refused in **356ms**. A dedicated 20/min export rate limit was added; the general 60/min limit alone let one client hold both workers continuously.
- **~~The model store's memory cap was an estimate against a real container limit~~ → FIXED.** `sizeOf()` under-counted actual heap by a measured **2.68x** (415KB estimated vs 1113KB real for a 21-page lecture), so a 512MB "cap" would have admitted ~1263 documents holding **1.34GB** — past the 1536MB heap ceiling, before the 2GB container limit even trips, i.e. an OOM under sustained load taking every in-flight document with it. `OVERHEAD_FACTOR` now makes the unit real bytes, and a count ceiling was added because the byte figure is an estimate. Locked by `test/store.test.js`.
- **~~Nothing ran the tests~~ → FIXED.** `.github/workflows/ci.yml` runs the hosted suites on every push **and builds the Docker image and boots it**, which is the cheapest way to turn the never-built image from inference into evidence.

- **~~The Docker image has never been built~~ → VERIFIED 2026-10-22 by CI.** The first push to `main` built the image and booted it on GitHub Actions (`readyz` answered); the hosted suite passes there too. Still unverified: the Oracle ARM64 host itself and graceful shutdown on Linux.
- **PPTX fidelity verification does not exist on the hosted build** (by necessity, not oversight): the visual proof renders each slide through *real desktop PowerPoint* over COM, which needs Windows + Office. The hosted export uses `writePptx` + `refont.js` and is genuinely editable, but carries no SSIM evidence. The desktop app remains the only place a verified export can be produced. Trigger: expecting `fidelity-report.json` from the server.
- **Rate limits and the model store are per PROCESS, in memory.** Correct for one VM; wrong the moment a second instance exists, because limits then multiply and a model stored on instance A is invisible to instance B. Moving both to Redis is the change to make at that point — not raising the numbers. Trigger: horizontal scaling.
- **Chromium `printToPDF`'s `scale` option silently CLIPS content** (found and worked around 2026-09-02): scaling the deck 4/3 to convert CSS px into PDF points produced a correctly-sized page with **word recall 0.759 against 0.990** — text past the original viewport is simply dropped, with no error. `scale` repaints without resizing the layout box. CSS `zoom` resizes the box, and gives true 713x488 geometry AND 0.990 recall. Trigger: any future change to `server/lib/render-pdf.js` that reaches for `scale`.

- **~~Hosted PPTX export discarded every user edit~~ → FIXED 2026-09-10 by `engine/apply-edits.js`.** PPTX was written from the stored model while PDF was rendered from the edited HTML, so one session produced two different documents and the PPTX silently shipped the ORIGINAL text. Proven before the fix (edit absent / original present) and after (edit present / original absent). The browser now sends the canvas state — `data-id`, text, bbox per object — and the server folds it into a CLONE of the stored model before writing. Fidelity contract: an untouched object keeps its runs byte-for-byte; an edited one collapses to a single run keeping the first run's styling, and its `srcW`/`charactersMissing`/`lamAlefLost` are cleared because they describe the extraction, not the human's corrected string. Locked by `test/apply-edits.test.js` (10 cases) and `test/server-hosted.test.js`. **Still open on the DESKTOP shell:**
- **PDF-imported decks export PPTX through the WRONG writer on the DESKTOP shell** (open, by scope): the agreed routing is "PDF-in uses the pdf=ppt exporter", but an imported PDF becomes deck HTML, so `#btn-export-pptx` sends it through `src/pptxFidelity.js` like any HTML deck. The corpus-locked writer (`engine/src/pptx/write.js`) and **`engine/src/pptx/refont.js`** — the fix that stopped delivered decks naming fonts the reader cannot load — are therefore NOT on this path. Doing it properly means keeping the model alive after import and round-tripping edits back into it, otherwise routing to the engine silently discards everything the user edited. Trigger: import a PDF, click PPTX. **Decide deliberately; do not "just route it".**
- **~~PPTX export fails at the FINAL step when the destination is on another drive~~ → FIXED 2026-10-22.** On `EXDEV` the commit copies the verified deck next to the destination and renames it there, so the replace stays atomic and a failed copy never leaves a half-written file. Locked by `test/pptx-atomic-commit.test.js`, including a real D:→C: commit on the development machine.
- **~~PDF import blocks the Electron main process~~ → FIXED 2026-10-22.** Reconstruction runs on a reused worker thread (`engine/import-worker.js`); the main process answered within 9ms throughout a 21-page import. If a worker cannot start (e.g. a packaged build that cannot load ESM from the archive) import falls back to the main process rather than failing. Locked by `test/electron-pdf-import-responsive.test.js`.

Trigger: PDFs whose cell text is wider than the cell the extractor recovered.

- **~~Doctor silent on external `@import`~~ → RESOLVED 2026-07-16 by Rule 19b** (`fonts-external`, commit `c698efa`): the doctor now emits a deck-level warn when the deck loads fonts from a web-font host (`@import`/`<link>` to fonts.googleapis.com, typekit, bunny, …), routing the user to 🔤 embed. - **~~Theme kits cannot recolor hardcoded hex~~ → RESOLVED 2026-07-26** (kit variable adoption + doctor Rule 21 `hardcoded-colors`): kits now adopt every color variable the deck invented (`--gold`, `--light-cyan`, `--green` → nearest kit token, declared inside `ve-theme`), and the doctor rewrites literal colors in CSS rules, inline styles and SVG `fill=`/`stroke=` attributes to `var(--ve-k-token, #original)`. - **Monospace stays off-brand** (accepted 2026-07-27): `<span>`/`<code>` set to the generic `monospace` family (variable and formula notation — 10–34 elements in the real lectures) renders the system mono font, because MiM ships no monospace face. Forcing Diodrum on them would break the column alignment the notation relies on. Everything else in those decks renders Lyon or Diodrum. Trigger: decks with mathematical notation.
- **A deck's own `font-family` rule can still outrank the kit's role rules** (accepted, unchanged): the kit sets headings via `.slide h1` (0,1,1) and body via `body`/`p`/`li` — a deck rule with higher specificity (e.g. `#id .cover .title`) keeps its own family. Trigger: Studio charts/diagrams in the Electron app. Harmless meanwhile — Rule 21 catches them.
- **Brand snapping flattens multi-stop gradients** (accepted 2026-07-26): when every stop of a `linear-gradient` snaps to the same kit token the gradient renders as a flat color (Lec35's green cover → solid MiM purple — clean and on-brand, but no longer a gradient). - **~~PowerPoint COM littered the project root with junk directories~~ → FIXED 2026-08-16**: the PowerShell/COM render inherited the caller's cwd, and PowerPoint resolves some cache folders relative to it, creating directories named from uninitialised bytes (34 of them, each holding an empty `Microsoft` folder) during the corpus runs. - **PowerPoint resolves bidi neutrals differently from Chromium** (2026-08-16, diagnosed, fix deliberately deferred): a colon or bracket sitting between an Arabic run and a number/Latin run lands on the other side of it — «الدرس 33: الحل» exports as «الدرس :33الحل», and the following space is swallowed. Reproduce with `node verify-pptx-corpus.js test/fixtures/bidi-deck.html --no-cache`. **Our data is not at fault:** the measured line runs are in LOGICAL order and `concat(runs) === line.text` exactly (verified), and the paragraph carries OOXML `rtl="1"` — so the text handed over is the correct source string and PowerPoint's own bidi algorithm settles the neutral differently. The standard remedy is to wrap number/Latin segments in Unicode isolates (U+2066 LRI … U+2069 PDI), which forces both engines to the same resolution. **Not done, on purpose:** it injects invisible control characters into the user's exported text, which the structural audit compares against `expectedDomText` and which would then live inside every deck the user edits by hand. Cost/benefit is currently poor — the isolated `bidi-deck` fixture still scores **0.9262 SSIM and verifies**, so this is cosmetic-but-visible rather than a gate failure. Revisit if a user complains about the punctuation, or if per-segment measured geometry ever lands (which would allow positioning each segment instead of mutating text).
- **PPTX bake crops carry their backdrop, and clip what overflows** (2026-08-14, mission 033): a baked element (inline SVG, filtered/blended/transformed box) is a crop of the composed page at the node's bounds, so it includes whatever is painted behind it, and any label the element draws *outside* its own bounding box is cut off — visible on the Lec32 linear-programming figure, whose axis labels overflow the `<svg>` box. Overlapping higher-z text above a baked element also double-renders. Trigger: any deck with inline SVG. The self-heal loop (mission 035) is the net; a per-element isolated capture was deliberately rejected in the plan (D1).
- **~~PPTX export: cairosvg not installed~~ → RESOLVED 2026-08-14 (mission 033)**: the cairosvg/inkscape/placeholder rasterizer tiers are gone. Chromium is now the only rasterizer (plan decision D1) — unmappable elements are captured by the same engine that renders the fidelity reference, and a missing capture is a hard error instead of a labeled placeholder that the structural audit could not distinguish from a real picture.
- **Inline `<svg>` was silently dropped from every PPTX before 2026-08-14** (fixed in mission 033, recorded because it explains old exports): `forbiddenTags` held `'SVG'` but DOM `tagName` for a foreign-namespace element is the authored lowercase `'svg'`, so the check never matched. The SVG was walked as ordinary layout nodes that emit nothing — no error, no placeholder, just a missing diagram. Verified in the live DOM and fixed by upper-casing the tag before the lookup.
